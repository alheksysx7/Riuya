Alcance: seis tablas privadas, catálogos de ocho personajes y seis categorías, roles permitidos user/editor/admin y dos funciones públicas de lectura. No se crean cuentas ni se concede ningún rol a personas; sesiones y gestión de roles se implementan en zonas posteriores. Biografías y retratos permanecen pendientes de integración y validación.

## Cómo revisar

1. Abrir Supabase Studio en http://127.0.0.1:54323 y entrar en SQL Editor.
2. Ejecutar SELECT * FROM api.list_characters(); Deben aparecer Rami, Beatriz, Leo, Dmitri, Naoki, Salma, Tove y Kavya en ese orden.
3. Ejecutar SELECT * FROM api.list_categories(); Deben aparecer Política, Economía, Tecnología, Ciencia, Sociedad y Cultura; la API ordena alfabéticamente.
4. Para repetir la prueba de base desde la carpeta app con Node 24: npm run test:db. El script usa Docker, transacción y ROLLBACK; no borra datos de trabajo.

## Evidencia

- Migraciones aplicadas sobre Supabase local y reconstruidas en una base desechable separada, usando una tabla Auth simulada; no es una reconstrucción completa de la pila Supabase Auth.
- Pruebas SQL: orden/cantidad, duplicados, noveno personaje, slug inválido, permisos de esquema, RLS y llamadas anon/authenticated; prueba transaccional con ROLLBACK.
- HTTP con clave anónima: ocho voces y seis categorías; esquema private rechazado. No se ha probado una sesión JWT real; queda en Z04.
- Las funciones públicas usan un rol dedicado NOLOGIN y sin superusuario/BYPASSRLS; no puede leer perfiles ni modificar catálogos.
- Persisten ocho alertas moderadas de herramientas de desarrollo identificadas en Z00; no se han modificado ni considerado resueltas.
